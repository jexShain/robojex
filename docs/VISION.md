## 一、用户原始输入（原话存档）

### 1. 总体愿景（2026-08-21）

> 我最终想法是这个这不只是软件，而是人工智能系统，能后续自动根据用户显卡配置，安装 Mage-VL 这种识别视频的大模型运行，学习屏幕+键盘或鼠标点击或输入内容（robojex 的学习模式，用户主动打开让学习的）。我要的类似于 Iphone 的 Apple Intelligence 的控制屏幕和键盘鼠标、完全可以控制电脑的软件，初期不在乎安全性（因为只能推荐在测试系统/虚拟机使用），只在乎能自主学习什么东西，揣摩用户技能和平时使用习惯。

要点拆解：
1. **不只是软件，是人工智能系统** —— 定位升级
2. **自动根据显卡配置安装视频理解大模型**（GPU 检测 → 自动选型/下载/运行）
3. **学习模式（用户主动开启）**：同步学习「屏幕画面 + 键鼠点击/输入内容」
4. **终态类似 Apple Intelligence**：完全控制屏幕和键盘鼠标
5. **初期不投入安全性**（定位测试系统/虚拟机），把精力全部投入自主学习能力

### 2. 学习模式与控制路径（澄清问答原话）

> 比如我让 robojex 进入屏幕学习模式，可能会开很久很久，视频大模型就学习转化自然语言，robojex 通过自然语言去调用 AI 提取有用的信息，理解、学习，总结，后续能按视频模型+自行电脑控制。电脑控制也有现有方案，我想着开启后 AI 使用 browser-use 这种操作去控制电脑，类似于开源远程桌面的这种，robojex 自己开这个服务然后调用浏览器，浏览器里操作桌面，实现准确的桌面控制和接管。

要点拆解：
1. 学习会话**可以开很久**（小时级/天级），需要分段处理与磁盘存储
2. **感知层**：视频大模型把屏幕内容流式转化为**自然语言叙述**
3. **认知层**：robojex 拿自然语言调用 AI（现有 decide 模型）**提取有用信息、理解、学习、总结**
4. **执行层（后续）**：视频模型理解 + 自行电脑控制
5. 用户设想的控制实现：**browser-use 式**——robojex 自己开远程桌面服务，AI 通过浏览器操作桌面里的画面，实现准确控制与接管

## 二、现状与差距（2026-08-21 代码探索结论）

v0.1.0 的 RoboJex 是"编排型"框架，与新愿景的差距：

| 能力 | 现状 | 差距 |
|---|---|---|
| 视觉感知 | 32×32 灰度 pHash 去重 + tesseract OCR 文本；**图片从未进入 LLM**（`llm.ts` 无多模态字段） | 需要真正的视频理解（VLM） |
| 人类输入记录 | **完全没有**。只有热键组合检测（xinput RawKey）和 xprintidle 空闲查询，无事件级记录通道 | 学习模式的核心输入缺失 |
| 本地模型/GPU | **零代码**。全仓库无 gpu/vram/cuda/llama/ollama/vlm 相关实现 | 全新建（检测/选型/下载/服务化） |
| 桌面接管 | takeoverd 仅 X11 实现（import 截屏 + xdotool 注入），WSL2 降级 | 需要平台抽象，Windows 路径未定 |
| 键鼠注入通道 | xdotool（Linux） | 需要统一控制通道（VNC） |

## 三、技术事实备查（2026-08-21 检索）

- **Mage-VL**：微软 4B codec-native 流式多模态模型，Qwen3-4B 底座 + 自研 Mage-ViT 视觉编码器；直接读视频压缩码流，视觉 token 比"均匀抽帧拼接"少 75%，支持流式长视频。
  - 权重：<https://huggingface.co/microsoft/Mage-VL>
  - 本地部署路径：**Python transformers**（当前唯一 NVIDIA 路径）；MLX 8bit 仅 Apple Silicon（<https://huggingface.co/mlx-community/Mage-VL-8bit>）；SGLang 支持跟踪中（sglang issue #32646）；**暂无 GGUF/llama.cpp/Ollama 版**。
  - 结论：visiond 需按「模型注册表」设计——每档显卡映射 {模型 × 运行时}，Mage-VL 走 transformers，Qwen2.5-VL/Qwen3-VL GGUF 走 llama.cpp 兜底，后续 Mage-VL 出量化版即插即换。
- **browser-use**：成熟的 AI 浏览器操作开源方案，用户设想的控制层参照物。
- **noVNC**：浏览器里的 VNC 客户端，成熟方案；人在其中操作 VM 时，键鼠事件天然流经 VNC 服务器，可被完美录制。

## 四、三个候选方案

### 方案一：VNC 中枢桥 + 独立 visiond + 学习管线（推荐）

```
VirtualBox/VMware 虚拟机 (VNC server)
        ▲
        │ VNC 协议（画面流↓ 输入事件↑）
┌───────┴────────┐
│     vncd       │  唯一的 VNC 客户端（takeoverd 新模块）
│  一条通道四路分发 │──① web 控制台 noVNC 视图 ← 人从这里操作 VM
└───┬────────┬───┘──② 录制流：画面帧+键鼠事件，同时间戳落盘
    │        └─────③ AI 控制通道：往 VNC 注入输入事件（M2）
    │              ④ 实时帧 → visiond
┌───┴────────┐
│   visiond  │  本地视觉推理服务（独立进程，Python 生态）
│ GPU检测→选型 │  nvidia-smi 探 VRAM → 查模型注册表 → 自动装运行时
│ →下载→服务化 │  → 下权重 → OpenAI 兼容 HTTP API，视频段→自然语言叙述
└───┬────────┘
┌───┴────────┐
│  ceo-core   │  学习管线扩展：录制分段→叙述→LLM提取→技能卡+习惯
│ (jex 循环)  │  runtime/skills/*.md 技能库 + web 控制台 Learning 视图
└────────────┘
```

**关键设计点**：人操作 VM 必须走 robojex 的 noVNC 页面（不是 VirtualBox 自己的窗口）——每次键鼠都流经 vncd 被录制，与画面帧**天然毫秒级同步**，无需任何平台原生钩子。

- 优点：一条 VNC 通道同时解决**学习录制、人类访问、AI 控制**三件事；跨平台一致（M3 真实 Windows 宿主接入时只换桥实现，上层不变）；visiond 独立进程，Python/模型环境与 Node 主进程完全解耦
- 缺点：人在浏览器里操作 VM（体验略逊原生窗口，noVNC 成熟可接受）

### 方案二：browser-use 式浏览器执行层

学习同方案一；AI 控制不走 VNC 直注——复用现有 `cdp.ts` 开 Chrome 加载 noVNC 页面，AI 用浏览器自动化操作桌面（点 canvas 坐标、发键盘）。
- 优点：复用 CDP 现有代码；AI 操作过程在浏览器窗口肉眼可见
- 缺点：多一层间接（延迟 + 坐标映射精度损失）；视觉输入是浏览器截图而非原始 framebuffer
- 定位：适合作为方案一之上的**演示/围观模式**，不做底层通道

### 方案三：旁路只读录制（最小版）

robojex 只读监听 VNC 画面，人直接在 VirtualBox 窗口操作。
- **致命缺陷**：拿不到输入事件——人在 VirtualBox 窗口的键鼠不经过 VNC，学习只能靠画面变化反推动作，"点了哪里、输了什么"全靠猜
- 结论：**不推荐**；仅作为未来"无桥环境"的降级模式保留
